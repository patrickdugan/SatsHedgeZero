# SHZ-RGB-01C | Evidence observers and coordinated checkpoints

Development-only reference. Existing sats clearing, DLC signatures, user credit and payment dispatch are untouched. The journal still requires independent reserve, BTC, RGB and conflict keys. This extension introduces normalized receipt checks and the local checkpoint reference implementation.

## Evidence boundary

The SHZ reserve record does not contain a BTC funding output script or RGB payer identity. The same configured reserve authority signs a separate canonical funding binding containing those fields, full reservation and journal identity (SHZ/RGB/FUNDING-BINDING/V1). Preserve that signed binding and observer evidence in separate durable records for audit. This reference does not persist them or implement signer services. The authorization service must enforce a unique funding destination per withdrawal and verify a committed SHZ entitlement, allowed asset, oracle quote, conversion provider and fee ceiling before signing. Those checks remain outside the prototype.

BTC verifier calls a trusted independent Bitcoin Core regtest RPC interface: getblockchaininfo, getblockheader, getblockhash, getblock, getrawtransaction with blockhash, then a second getblockchaininfo. It checks the authorized native segwit output script, exact satoshi value, txid/vout, block membership, active chain and >=6 confirmations; a changing tip aborts the observation. The stable proof ID is domain-separated hash of network/txid/vout, excluding block hash. No requirement that an already delivered output remain unspent. Core is a trust anchor here, not an SPV proof. A matching output does not prove the sender's identity or that it was funded for this obligation; require unique preauthorized scripts, provider controls and independently reconciled ownership. The test RPC is synthetic, not a live Core node. Caller must supply a trusted isolated RPC client.

RGB LN verifier requires normalized records from separately authenticated payer and receiver observers. Both must bind the payment hash, correct node identity/direction, terminal status, exact asset ID, units, carrier msat and payee. The payer preimage must hash to the invoice payment hash. Stable ID derives from network/payment hash; no preimage leaves the verifier. This is a strict application contract, not an assertion of the raw beta.5 RPC schema. Native WDK responses remain opaque; mapping, authentication, independent balance/channel reconciliation, invoice validation and consignment/force-close evidence require actual funded fixture work. The function identity check alone does not establish independent observers.

The reconciliation builder checks both observations refer to the same reservation and funding binding. It is not a signature or proof verifier: its plain-object inputs are forgeable. Each observer must rerun its own verification, compare the full authorized binding and independently sign the exact journal reconciliation event before append. Do not expose signing via an unauthenticated caller or treat an SDK status as permission to sign. No live signer service or automatic credit path is included. Continuous reorg monitoring and signed conflict reports are still required. A six-block policy reduces exposure and does not repair upstream P03 reorg semantics.

## Checkpoint boundary

Separate directory checkpointStore binds journal ID and exact seq/digest; compareAndSwap only permits one-step advancement and serializes writers using an exclusive directory lock. Writes fsync a private temporary file, rename and fsync its directory. The coordinator checks the current pin, appends/fsyncs journal, CAS-advances checkpoint, checks acknowledgment, then returns the new tip. Any failure fences the coordinator. This is deliberately conservative, including rejected transition errors. Reopening requires exact equality and revalidation; no stale-lock takeover, truncation or automatic pin correction. Never dispatch until a submit frame and checkpoint are both acknowledged; never retry a submitted/ambiguous event. Even a crash before actual dispatch can require manual reconciliation. No dispatch API exists.

The local reference is a separate path, not a separate host/trust domain. It cannot detect rollback of both directories or privileged manipulation. Production needs an independently administered durable CAS service, authenticated clients, cross-journal receipt uniqueness and recovery procedure for incomplete CAS and stale locks. A crash leaving a stale .cas lock or temporary file needs operator review; no automated cleanup. The same directory must never be shared across trust domains. No distributed atomicity, exactly-once payment or power-loss guarantee is claimed.
